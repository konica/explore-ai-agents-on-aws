How the services relate to each other

Reading the diagram as a dependency chain rather than a picture: each service exists to serve the one after it.

ServiceRole in this deploymentDepends on / feedsConfig key
AWS CodeBuild Builds your Dockerfile into an arm64 image — you never run docker build yourself. Reads your code → writes to ECR codebuild.project_name
Amazon ECR Stores the built image so the Runtime has something to pull each time it starts. Fed by CodeBuild → pulled by Runtime ecr_auto_create: true
IAM execution role The permission slip the Runtime presents when it calls other AWS services on your behalf. Created independently → assumed by Runtime execution_role_auto_create
Bedrock AgentCore Runtime The hub. Hosts your container, terminates the public HTTP call, and is the only service that talks to everything else. Depends on ECR image + IAM role → calls Bedrock Runtime, emits to CloudWatch deployment_type: container
Amazon Bedrock Runtime Runs the actual model inference behind the Converse API — the "thinking" step. Called by AgentCore Runtime → invokes Claude Sonnet 4.5 model_id in agent.py
CloudWatch + X-Ray Passive observer — receives traces and logs from the Runtime, never called on the request's critical path. Fed by AgentCore Runtime only observability.enabled: true
AgentCore Memory Would let the agent recall past sessions — currently no memory resource exists to depend on. Not wired to Runtime memory.mode: NO_MEMORY
AgentCore Identity Would let the agent authenticate callers or act on behalf of a signed-in user — unset, so anyone who can reach the endpoint can call it. Not wired to Runtime oauth_configuration: null
Amazon S3 Would hold deployment artifacts if the toolkit needed staged storage — this path isn't used for a direct container build. Not wired to Runtime s3_auto_create: false
